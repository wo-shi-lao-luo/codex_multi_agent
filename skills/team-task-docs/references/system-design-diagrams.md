# System Design diagram guide

Start with the question a reviewer needs to answer. Identify the entry, the input, the transformation or decision, and the result before choosing a diagram. The [System Design template](../assets/system-design.md#proposed-system-and-key-flows) defines when to draw, split, or link runtime views. The table helps choose how to show each flow and when a supporting view explains another decision.

## Choose the view

| Question to answer | View | What to draw and how to read it |
| --- | --- | --- |
| Who talks to whom, in what order, and when is the result safe to show? | **Sequence diagram** | Read top to bottom. Name the participants and label calls, events, and replies with the effective payload and relevant identity or version. Distinguish synchronous calls from asynchronous messages and acceptance from completion. Mark the approval, write or commit, acknowledgment, and readback when they affect the result. Show conflict, timeout, retry, or cancellation on the same path where they share the interaction. |
| Why does this input take one route, and who owns the next action? | **Flowchart or swimlane activity diagram** | Follow the arrows from the trigger. Label each decision with the rule or evidence and its outgoing conditions, including the default or insufficient-evidence route when relevant. Use lanes for responsibility, and show parallel work and the condition for joining when they change the result. For AI, identify model decisions and tool proposals and show the host checks, human approval, and stop conditions where applicable. |
| Which states can one object enter, and what can still happen afterward? | **State diagram** | Read each edge as an event, a guard if needed, and the resulting state. Identify the stateful object and source of truth. Mark initial and terminal states, who can cause each material transition, and effects or restrictions on retry, cancel, restart, and late or duplicate events. Keep independently changing lifecycles explicit so UI state, approval state, and persisted business state can be checked separately. |
| Where did this data come from, how did it change, and who can consume it? | **Data flow or lineage diagram** | Follow named data from a source through processes to stores and consumers. Mark material transformations, source of truth, stored versus derived data, and IDs or versions needed to trace or reproduce an output. For sensitive data, show the external actors, trust boundaries, data crossing each boundary, and the responsible protection or authorization control. Arrows represent data movement or derivation. Mark order separately if it matters. |
| Which records are related, and how is the relationship enforced? | **Entity–relationship diagram (ERD)** | Read each edge as a relationship and use cardinality and optionality to show which records may or must exist together. Include relevant keys, relationship ownership, version or history references, and links to applicable constraints and deletion or migration behavior. To review the actual order of writes, pair it with the applicable runtime view. |
| What sits inside this system, who uses it, and what owns a boundary? | **C4 system context, container, or focused component view** | Start with people, this system, and external systems at context level. Zoom into the affected applications and stores at container level. Use a component view for a material boundary inside one application. Name ownership and the purpose of each relationship. Reuse the existing architecture view when its scope fits. |
| Where does code run, and which environment or connection affects the design? | **Deployment diagram** | Read nested nodes as environments or places where instances run. Map affected applications, workers, and stores to those nodes. Mark material network or isolation boundaries, storage location, failover, or routing. For a staged migration, use an accompanying sequence or flow when cutover, mixed versions, verification, or rollback depend on order. |
| What does a user do, see, or resume across screens or channels? | **User flow or journey view** | Start with the user's goal and entry point. Walk visible actions, screens, and feedback through completion or recovery. Link the step needing a technical decision to its runtime view. Reuse the project's existing UX design or prototype when it already shows the relevant interaction. |

## Make it readable and reviewable

- Put the question, scope, and relevant baseline or proposed state in the title or caption. Use the project's existing names and consistent levels of detail. Explain arrow styles, boundaries, or colors when they carry meaning. Use labels so the meaning remains readable without color.
- In a runtime view, carry concrete data through the material boundaries and name the observable outcome. Use the same IDs, versions, and names across linked views. Point to the matching acceptance case IDs. For a supporting structural view, identify the decision, boundary, or invariant it clarifies and link to the relevant runtime scenario or contract.
- Read the diagram from the entry or scope line and follow a labeled path to its result. If the reader cannot tell who decided, what moved, or how completion is observed, add the missing label or note. If a view must answer a different design question, link a narrower view at the handoff. Use a concise numbered explanation when that is sufficient. Review the rendered diagram in the target document viewer when available.

## Example — attachment import

| Decision being reviewed | How the design can show it | Example acceptance case IDs |
| --- | --- | --- |
| Classify the same upload request | A flowchart follows file `A12 v2` from upload. The host checks its metadata and routes it to direct import, a review proposal, or an unsupported-format result. The review route links to the approval flow. | IMP-01 routing |
| Save an approved import | A sequence diagram follows the proposal for `A12 v2` through approval, a version check, and commit. The returned receipt permits the UI to show completion. Cancellation and a stale-version conflict branch at the affected step and show the resulting state. | IMP-02 save, IMP-03 conflict, IMP-04 cancel |
| Review what retry may do | A state diagram helps if an import job can run across requests. For `J42`, show when retry can move a failed job back to queued, which state is persisted, and how a late worker result is handled after cancellation. | IMP-05 retry, IMP-06 late result |
| Trace an imported asset back to its source | A lineage view follows a different entry, the saved asset ID, back to the retained source version and import run. An ERD is useful if the review also needs to decide how asset versions, runs, and stored evidence are related. | IMP-07 source and version lookup |

Use only the views needed for the decisions under review. For a different change to the same feature, the existing views and one short explanation may already cover the decision.

## Sources and design examples

- C4 defines structure, runtime interaction, and deployment views at different scopes. Its review checklist checks scope, element roles, relationship labels, and notation. [C4 diagrams](https://c4model.com/diagrams) · [C4 review checklist](https://c4model.com/diagrams/checklist)
- arc42 selects representative runtime scenarios and uses swimlanes for responsibility. It also shows how to shorten a sequence to its important decisions. [arc42 runtime view](https://docs.arc42.org/section-6/) · [Swimlanes](https://docs.arc42.org/tips/6-7/) · [Partial scenarios](https://docs.arc42.org/tips/6-6/)
- Kafka KIP-98 uses numbered operations to connect transaction messages and writes to accompanying explanations. AWS's outbox example shows distinct outcomes when a write and an event publication are separated. [Kafka KIP-98](https://cwiki.apache.org/confluence/spaces/KAFKA/pages/66854913/KIP-98%2B-%2BExactly%2BOnce%2BDelivery%2Band%2BTransactional%2BMessaging) · [AWS transactional outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)
- Stripe Ledger illustrates state transitions and historical reconstruction. Anthropic's workflow examples show routing, parallel branches, and aggregation. [Stripe Ledger](https://stripe.dev/blog/ledger-stripe-system-for-tracking-and-validating-money-movement) · [Anthropic workflow diagrams](https://www.anthropic.com/research/building-effective-agents)
- Microsoft illustrates trust boundaries in a data flow. OpenLineage connects input and output datasets through transformations and run identities. [Microsoft data-flow elements](https://learn.microsoft.com/en-us/azure/security/develop/threat-modeling-tool-feature-overview#stencils) · [OpenLineage object model](https://openlineage.io/docs/next/spec/object-model/)
- Mermaid documents notation for runtime and data model views. The GOV.UK service manual describes mapping from the user's perspective across stages and services. [Mermaid examples](https://mermaid.js.org/syntax/all-examples) · [GOV.UK user journeys](https://www.gov.uk/service-manual/design/map-a-users-whole-problem)
