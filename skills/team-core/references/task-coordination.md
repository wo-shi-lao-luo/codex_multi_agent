# Optional task coordination

Use this contract only when an authorized task has multiple independently deliverable work packages, meaningful handoffs, or sustained assignment that benefits from coordination. Small or clear work stays on the existing direct path. The queue is optional and does not add a planning, database-installation, or runtime prerequisite to ordinary Team work.

## Authority and activation

The Lead decides whether coordination is worthwhile, creates and approves packages, chooses eligible work, starts or resumes host agents, answers questions, reconciles evidence, and integrates results. The queue is a passive record and query interface: it never calls a model, creates or wakes an agent, retries business work, or schedules work by itself. A local board is bound to one explicit coordination root, one current Lead, and supported local storage. It registers the main checkout plus explicitly verified linked worktrees from the same Git common directory; another clone, repository name, matching relative paths, or machine does not establish shared identity. Board workspaces share task state, while each retains its own execution-root binding. Treat project queue data as local and ignored. Recheck the root binding before any operation that can claim or mutate a package.

Use a board only when its optional generated runtime is present, its manifest/source correspondence is verified, and the queue is useful. Board operations require Node.js >=26.13.0 and <27 with built-in `node:sqlite` and SQLite >=3.54.0. Windows x64 is the only tested platform; other operating systems remain unverified. A source checkout or a planned runtime path does not establish an installable artifact, installation, or active-session loading. If the runtime is absent and there is no active board, keep using the existing direct workflow. If an existing board is unavailable, incompatible, or has an unknown schema, stop new claims and mutations, preserve the database and in-flight facts, and arrange a safe handoff through the Lead. Never initialize over it, assume it is empty, or silently create a replacement queue.

The installed entry is `node <team-core>/runtime/task-board/cli.mjs`; development uses `packages/task-board/src/cli/cli.mjs`. Run `help --operation <command>` for that operation's current required, optional and conditional fields. Help and the pure `session-path` operation are data-only and need no Board. Run `node packages/task-board/src/cli/cli.mjs runtime-doctor` from the source checkout or `node <team-core>/runtime/task-board/cli.mjs runtime-doctor` from an installed Skill; this diagnostic checks the supported Node.js and built-in SQLite prerequisites without opening a Board, downloading software or changing global configuration. Retained `service-status`, `service-stop`, and `service-open` use the confirmed flat service identity without database access or project/board paths. Database operations require explicit `--project-root` and `--board-path`, plus `--session-key` when operating on a bound Board; send each bounded JSON request through `--stdin` or `--input` as its operation help specifies. Prefer protected stdin transport for caller-held credentials; do not put credentials in task text, ordinary logs or command arguments. Generate and retain the required random tokens; callers never submit their own digest or SQL. Do not guess fields from this guide or invoke operations absent from the verified package's help.

## Executor identity, Lead-inline work, and registered workspaces

The execution protocol is schema 4. Migration is explicit: schema 3 to 4 requires the dedicated migration operation; historical schema 2 to 3 remains a separate legacy route. Restore-new-target preserves the backup schema. Never auto-migrate, reset, or relabel an older Board as schema 4. The 3-to-4 migration preserves declared eligible roles and named logical resource keys, and rebuilds legacy path-resource keys against the registered `main` checkout so they continue to conflict with new physical-path reservations. It invalidates pre-4 executor/evidence authority and revokes old grants; preserved contract data does not preserve stale authorization.

A registered worker/assignment has an execution mode and authorization separate from the actor performing it; task fields separately opt into Lead-inline and bind a workspace. `direct` authorizes its registered worker to execute under the worker grant. `lead-proxy` lets a read-only role report evidence for the Lead to record; the proxy itself cannot claim, submit, or mutate Board state. `lead-inline` records work performed serially by the actual current Lead, using Board `leadId` as the executor identity; it never creates or wakes a child. `lead-recorded` records an actual production worker's result through a Lead record operation and does not grant that worker database write permission. Board protocol pass-through never auto-spawns.

Responsibilities and process identity are distinct. The main Lead may read the applicable Skills, own assigned production work, perform coverage planning, create or complete the required packet, and run required checks serially. Report those checks as Lead self-check. Do not fabricate a specialist, child, role, model, reasoning effort, host identity, or independent evidence. Keep required independent review/evaluation gates genuinely independent. If host metadata does not establish an identity, represent it as unknown. Optional `principal` data may contain `hostId`, `agentId`, and `evidenceRefs`; the server derives `executorKey`. Observed runtime identity fields (`role`, `model`, `reasoningEffort`) remain null when unobserved. Task fields include `requiredSkills[]`, `responsibilities[]`, `allowLeadInline` (default false), and `workspaceId` (default `main`). A work scope may be a legacy string or typed `{workspaceId, path}`; source refs may optionally specify `workspaceId`.

Independent policies identify required checks by ID and exact kind (`independent-review`, `independent-evaluation`, or `independent-test`), mapped respectively to `team-reviewer`, `team-ai-tester`, and `team-tester` or `team-ai-tester`. A verification task binds its exact subject to a frozen submission. Acceptance `checkResults` satisfy only a current, closed check result from a known distinct principal with the correct registered role. Same-actor aliases, self-checks, unknown principals, and Lead-inline results cannot satisfy an independent gate. Never infer independence from different task labels, role labels, or agent IDs alone. Required-check bindings are durable evidence relationships, not dependency-graph edges. Reopening or invalidating a required checker after producer acceptance withdraws the producer result and its downstream consumption under normal invalidation rules, while retaining closed checker history; the check must be current and closed again before the producer can be accepted again. These evidence bindings must not introduce a dependency-graph cycle.

The Board has a bounded registered workspace list (maximum 100); the main checkout is registered by default. Additional workspaces must be actual Git linked worktrees in the same repository, verified through common Git directory and `git worktree list` membership. A separate clone or matching repository name is rejected. At claim and replay, bind workspace IDs and source refs to the current registry snapshot and revalidate. For multi-workspace direct execution, the worker's actual CWD must be inside its bound execution workspace, conveyed as trusted process context rather than caller JSON; legacy main-only operation preserves its prior path behavior. Workspaces are execution roots, not OS security sandboxes.

Path conflicts are checkout-aware: claims in different worktrees may write their distinct physical files, while physical path aliases still conflict. Named logical resources remain global across workspaces. Enforce resource, read/write scope, source, grant, replay, and evidence bindings against the registered workspace snapshot. Board database mutation permissions remain separate from filesystem write permissions in a workspace; a recorded Lead action cannot claim OS-level proof that was not observed.

Canonical Board operations include `lead-inline-assign`, `lead-inline-report`, `lead-proxy-report`, `lead-record-report`, `workspace-register`, and `workspaces`. Use the current package's operation help for fields and invocation; this document states behavior and field contracts, not a substitute CLI schema.
## Sources of truth

Keep requirements, approved intent, architecture, implementation task authority, and acceptance in their established sources. In an opted-in OpenSpec change, `tasks.md` remains the sole implementation task and progress list; a board does not copy or replace it. The board may map native task IDs to execution package IDs, but it does not edit native checkboxes or claim automatic synchronization. Work and other existing task authorities remain authoritative when OpenSpec is not active. Stage packets and verification records remain authoritative for test evidence and human acceptance.

The queue stores only coordination facts that cannot be reconstructed losslessly from those sources: package identity and mapping, Lead-approved assignment, eligible worker references, claim and authorization versions, reservations, execution phase/progress, blocker and question state, handoff/release history, evidence references, and audit facts. Do not copy requirements, native task wording/progress, test results, or acceptance outcomes as a competing authority. The human-readable board is a projection and can be rebuilt; claims, reservations, and in-flight coordination facts cannot be inferred from a source task list after queue loss.

Use `source-check` for an authenticated, read-only candidate observation. Legacy string references remain explicitly `declared-unverified`; their presence is not filesystem proof. Typed references use `schemaVersion: 1`, a `kind` of `work` or `openspec`, `nativeTaskId`, and either `path` or `changeId`. A Work ID is a Lead declaration, not a parsed native task identity. OpenSpec requires its existing supported opt-in marker and an unambiguous native task ID; never create a marker just to make observation pass.

Review the actual authority before adopting a candidate digest. The Lead explicitly amends typed references with the observed semantic `expectedRevision`, approves the changed contract, reconciles the matched source, then grants execution. A hash is not user approval. Unpinned, changed, missing or ambiguous typed sources cannot authorize execution or accepted-result consumption. Reconcile observes actual files itself: caller-provided availability cannot override a mismatch. A negative reconciliation commits blocked/invalidation facts and retains existing allocations/history; it does not silently adopt a new pin, clear an owner or restore stale evidence. Normal OpenSpec checkbox progress preserves the semantic pin; changed wording or applicable source material requires reconciliation. Observations are bounded over the whole operation, including lineage: 32 typed references, 256 files, 1 MiB per file and 4 MiB total data read; after a limit, narrow the authorized source mapping rather than bypassing the cap. A single typed source, including an OpenSpec task's required snapshot, may exceed these limits; OpenSpec references have no generic file filter. Stop the affected claim and ask for a bounded mapping or design decision that preserves required source coverage; never truncate authority, hide files, switch to an opaque reference, or disable an active OpenSpec adapter just to fit the cap. Query candidates from a fresh checkout cannot reconstruct claims or acceptance.

## Package and assignment rules

The Lead defines each package's bounded outcome, source references/revisions, acceptance references, dependencies, eligible roles and authorized worker set, read/write paths, shared or exclusive resources, owner, and integration responsibility. Only the Lead approves scope and authorization changes. Ready is a computed query result; it is not a stored state or a permission grant. Claim only a Lead-approved eligible package after checking its current dependencies, authorization revision, worker identity, checkout binding, path/resource conflicts, and capacity.

Keep one current Lead and one owner for each shared contract and concrete write path. Independent packages may be assigned to multiple instances only when they are genuinely ready and independently deliverable, have disjoint write paths and resources, have a named integration owner, and the host can support them. This is a bounded exception to the usual one-production-writer default, not a mandate to parallelize or permission to restructure unrelated code. Follow [file ownership](file-ownership.md) for path-level freezes and safe writer transfers.

Keep role-selection and creation evidence distinct from runtime identity: an exact role selector and returned host handle prove only what was requested and created. Record any host-resolved role, model, and reasoning effort separately; leave each unknown when the host does not report it. Registering the selected role must not be presented as an independently resolved runtime identity. Do not infer capacity or successful dispatch from source configuration or a requested role label. Host dispatch outcomes that are unknown must be reconciled with the host before retrying; do not create a second worker or assignment blindly. The Lead owns capacity decisions and worker lifecycle. The board cannot establish that an agent is alive, stopped, or safe to replace.

Read-only Architects and Reviewers report findings to the Lead and never write directly to the board database. When a board operation is needed for their work, the Lead may record it as a proxy, preserving both the actual reporter and the Lead as recorder. A proxy write does not change the reporter's role or grant database access. Bounded simulation actors receive only their defined case packet: no board state, queue questions, unrelated case data, or scoring criteria. The outer Lead records actual execution facts; a simulation result is not product acceptance.

## State, questions, and safety

Use the implemented state transitions and evidence contract. In particular, `submitted` is not accepted completion; only the Lead closes a package after its applicable checks and gates are satisfied. For dependencies, `accepted-result` requires a closed package with still-valid evidence; `frozen-submission` is only for test/review work against a submitted, explicitly frozen writer scope and bound input/evidence revisions. A source/input change, reopen, cancellation, or returned implementation can invalidate downstream evidence: preserve history, stop affected work for Lead reconciliation, and do not unlock dependents from stale freezes. The Lead alone may release, cancel, reopen, transfer, or change a package's authorization. A transfer first establishes that the previous writer and its processes have stopped writing, invalidates the old assignment, and records the new owner atomically. Do not release a path or resource because an agent is quiet, a timeout elapsed, or a status appears stale.

Use the operation boundaries below; every logical mutation must authenticate the actor and compare current board generation, task revision, active assignment/worker where required, caller-held current credentials, and a unique `operationId`. The same `operationId` with an identical request returns the original result; reuse with different request content conflicts. Current credentials may be reused across distinct operations until revoked. Stale generation, task, assignment, authorization, or credential is a conflict; never silently refresh it. The database records immutable audit history alongside current state.

| Operation | Authority and effect |
| --- | --- |
| `assign`, `record-dispatch`, `claim` | Lead approves eligible worker/scope and records dispatch intent. A worker may claim only its authorized package. Dispatch states are `planned`, `known`, `failed`, `unknown`; planned/unknown is not a created worker. Reconcile an unknown host outcome before retry. Bind every claim to current generation, task revision, assignment and credential. |
| `report`, `block`, `submit` | Current assigned writer reports its own progress, blocker or evidence against the current execution. Only progress reporting may change the active execution state; it cannot accept, close, release or broaden authorization. |
| `lead-proxy-report` | Lead records a readonly worker's report with both actual reporter and Lead recorder in audit history. The proxy worker has no board write credential and cannot gain write paths from proxying. |
| `ask` | Current assigned writer may ask only about its current task/assignment and current source/authorization revision. It cannot create a grant or change scope. |
| `inbox` | Lead-only read. Reading lists questions but does not consume, acknowledge, or answer them. `ack-inbox` is a separate explicit Lead mutation and audit event. |
| `answer`, `ack-answer` | Lead answers the current assignment-bound question; the current owner separately acknowledges the answer. An approval-dependent answer remains blocking through answer and acknowledgement. Only an explicit Lead resolution backed by the required approval/source reference and current approval chain may clear the hold; if scope or contract changed, amend and reapprove it, then issue a new grant. Do not resume work automatically. |
| `inspect`, `show` | `inspect` is a full diagnostic snapshot available only to an authenticated Lead. Workers and anonymous callers use compact scoped queries; they cannot use Inspect to bypass context bounds. `show` retrieves one explicit task; optional history is bounded and carries the read revision metadata needed to detect a concurrent change. |

Only a Lead-authorized `report` for the current executing assignment may restore the executing state after a resolved hold, and only after the required approval is resolved and acknowledged. Answering or acknowledging a question alone never resumes execution. An old `Return`/`Reopen` phase may permit a new write only through its Lead-controlled transition, with prior frozen evidence invalidated as specified; question handling cannot simulate Return/Reopen.

Authorization is versioned and bound immutably to the board generation, package, worker, and approved scope. A stale authorization or generation cannot be refreshed by a worker or silently reused. There is no TTL-based lease, timeout-based takeover, automatic liveness inference, or elapsed-time authority. Progress estimates are informational; conditions that need a human decision remain pending until the Lead records an explicit answer or approval.

Questions are tied to the current package, assignment, source/authorization revision, and blocked step. Keep a thread limited to tightly related questions; do not broadcast across the project. A question or answer does not grant new scope. An answer that needs approval remains `approval-pending` until the authorized Lead records that approval and the current owner acknowledges the applicable answer; it does not itself change permissions, source intent, acceptance criteria, or task state. Inbox queries return up to 10 items by default (maximum 50); current Status returns 20 items by default (maximum 100); the fixed pending-question threshold is 10 and has no initialization override. At that threshold the assignment latch pauses new assignments until the Lead resolves the backlog. This threshold is a pending-work latch, not a 10-question notification batch or a time budget. It does not limit or suppress host-provided automatic messages/inbox behavior. Human and manual acceptance gates remain independent of queue state.

Successful `report` and `block` actions set server-owned `lastReportAt` in all supported execution modes: direct, Lead-proxy, Lead-inline, and Lead-recorded. The Lead-recorded report uses `lead-record-report`; callers cannot supply the timestamp. Submission alone is not a report. Exact receipt replay and all other mutations leave it unchanged. When a compact task summary includes a legacy task with no value, it returns `null`; a public legacy snapshot may omit the field. The UI must present either form as unknown, not infer a time from an older timestamp.

## Queries and context

Use compact, bounded summaries for Agent-facing Ready, Status, and current-task queries. Ready is filtered to the actor's current grants; current-task status is scoped to its owned task and direct dependencies. Paginate larger results with the supported cursor/`hasMore` mechanism, and fetch details or history by explicit package ID when needed. `show` history is separately bounded (20 default, maximum 100) and includes revision metadata so callers can detect a concurrent change. Do not treat a storage row cap as an Agent context budget. Only authenticated Lead Inspect returns a full diagnostic snapshot; it is not the routine Agent status response. Browser snapshots, subscriptions, and SSE refresh the human-readable projection only; they are never added to Agent context automatically.

For an assigned package, read the current assignment, its accepted brief, and only task-relevant sections of its linked authorities and references. Reuse still-valid accepted context; fetch more when scope, evidence, or an observed mismatch requires it. Do not sweep every linked document by default, impose a hard token cap, or require a second context ledger.

The read-only `Status` scheduling summary is computed for the requesting actor before task pagination and reports `totalTasks`, `readyTasks`, `stateCounts`, `activeAssignments`, and `unknownDispatches` within that actor's visibility. Workers receive `null` for `unknownDispatches`; the Lead receives the current count of unknown dispatch intents. This is an operational summary, not host capacity or liveness evidence: `hostCapacity` remains `null` for every caller, and a role match does not resolve an unknown dispatch. Keep the summary visible before the paginated task list so it remains useful when the current page has no ready task. It never creates assignments or schedules work.

Logical archive hides eligible work from default Status/Ready and browser views; explicit `show`/Lead `inspect` retain it. Unarchive is explicit and uses the current preview/classification/approval contract; reopen retains its normal gates and clears archived visibility. Neither operation erases history or shrinks SQLite. Revalidate current read/write scopes when claiming or transferring: a path that was safe before it existed can later become a link or alias. Queue checks do not lock the filesystem or prevent arbitrary direct writes.

For existing Board maintenance, begin with `maintenance-status` and `diagnose` for the explicitly selected Board. Use the existing preview and approval flow for each authorized archive, prune, restore, backup, or physical maintenance operation; do not invent a generic inventory action, run unattended cleanup, or infer deletion from age or space pressure.

`serve` opens a read-only browser view. Retain its one-use bootstrap link privately. Optional service control uses a separate caller-held `serviceControlToken` and the returned service/board/generation/URL/port identity; keep these outside ordinary task context. `service-status`, `service-stop`, and `service-open` accept that flat identity without a usable database or Lead credential. `service-open` obtains a fresh one-use browser URL; use current operation help for exact fields and limits. Never infer an owned service from a PID, port alone or repository name. A stop result of `stopping` is acceptance, not proof of completed cleanup. Close only the confirmed owned listener; it must not change worker, assignment or reservation state. Different services use independent browser cookies. These controls are not browser task-write endpoints.

## Browser presentation

Present a board only after the Lead has selected and authorized it. Start or reuse only the service whose ownership and identity are confirmed. Keep its service identity and control token private in the existing Work record or handoff; never place the control token in chat, logs, URLs, or board records.

On the first activation for the current chat, board, and generation, use `service-open` to obtain a fresh one-use browser URL, then use the available `open_in_codex` host tool to open it in the current chat's browser panel on the right. Follow the current operation help for exact input fields. Record the observed opening outcome and any confirmed tab identity in the existing private handoff as `not-attempted`, `queued`, `opened`, `link-only`, or `unknown`; do not create a separate registry. A successful `service-open` only mints a URL. A host result of `queued` means the request has not yet opened the panel; it is not evidence of an opened tab or visible rendering.

Do not open the panel again for subtasks, progress updates, or resume after a completed or unknown first attempt. If the host reports `queued`, wait for the user to return to the chat or check the owned tab later; do not reissue the link, invoke automatic navigation, or bring the chat to the foreground unless the user explicitly asks. If the host reports an unknown outcome, inspect or confirm the owned tab before retrying. Closing the panel must not take focus back from the user or stop work. Only an explicit user request to open or reopen the board authorizes another fresh one-use URL; reuse a verified tab when the host supports it. If a one-use URL expires or ticket capacity prevents minting, do not replay it or fall back to a permanent unauthenticated URL; wait for an explicit open/reopen request before obtaining a fresh ticket. If the host tool is unavailable, provide a readable ephemeral browser link and record `link-only`. Do not force an external browser or promise a permanent native sidebar.

SSE refreshes the human-readable view without agent screenshots, screen-reading, or model rounds. A closed panel does not stop the service or agents and is not cleanup authority. When the task ends, stop only the confirmed owned service as appropriate; preserve the board database and assignments. Host opening and visible rendering are conditional client capabilities, not guarantees for every Codex client.

## Main-session binding and labels

Use one Board for one MAIN user chat. Child agents inherit that main session's Board context and path; they do not select a Board from their own task or agent IDs. Pause and restart in the same chat reuses its bound Board. A new chat selects a separate Board; never adopt, merge, or share another session's Board automatically. Board separation does not coordinate file reservations between sessions.

Derive a new session Board's canonical directory from stable host and MAIN-session IDs, and its session key from host, MAIN-session, and project IDs, using the data-only `session-path` operation. Use current help for exact inputs and output. Project and session names are display labels only, shown as `projectName + " + " + sessionName`: never use names or titles as identifiers, path components, instructions, or as a reason to use random IDs or select an older Board. Require `--session-key` for new session-bound operations, and initialize only in the canonical session directory with the matching profile. A missing, malformed, or mismatched stable identity stops the affected new session workflow; do not fall back to a mutable title or legacy Board. Keep existing unbound Boards available only through deliberate legacy operations with an explicit path and no session key. Never auto-bind or rename them; new session-keyed flows must reject an unbound Board.

At start, resume, explicit reopen, and handoff, query only current project/session metadata for the identifiers and latest names. Compare normalized names with the bound profile and run Lead-only `session-sync` only when labels changed; consult current operation help for exact fields. If fresh names are unavailable, preserve the last known labels and report synchronization as pending. Do not claim an immediate rename event, poll a model, or change the native chat or project name. Label updates affect display labels only; they do not change Board identity, storage location, credentials, tasks, grants, results, or acceptance. Treat names as untrusted text and render them as text.

Before reusing a retained service or opening a Board, compare the freshly derived session key and canonical project root with the retained selection. A service bound to another session key must not be reused, and a cached URL alone does not prove it belongs to this session. Refresh current labels before minting a reopen URL. Missing stable identifiers stop new Board work rather than selecting a previous session. These identifiers separate cooperating sessions; they are not a security boundary against other processes or users on the same operating system.

## Failure, maintenance, and distribution

On database, integrity, backup, migration, generation, or schema uncertainty, fail closed: preserve the original database and recovery evidence, stop affected writes and claims, and have the Lead establish a safe continuation or recovery. Never delete and recreate, silently downgrade, auto-repair ambiguous state, release uncertain resources, or rebuild assignment facts from OpenSpec/Work. Maintenance and cleanup protect active assignments, dependencies, unanswered questions, evidence, idempotency records and recovery points. Use the following boundaries only when the current verified package advertises the operation; help supplies the wire fields, not authority to maintain a project.

| Operation family | Required boundary |
| --- | --- |
| `preview-archive` / `archive` | Explicit IDs, current classification, preview, revision and approval; `action: unarchive` uses the same reviewed contract. Unknown references remain protected. No automatic age-based deletion. |
| `preview-prune` / `apply-prune` | Only an approved exact prefix of transport change events. Preserve tasks, audit, receipts and protected references; older SSE cursors resync. Physical task deletion is unsupported. |
| `checkpoint` | One PASSIVE observation; actual busy/deferred counters, no business receipt. Never delete WAL/SHM files to force it. |
| `compress-backup` / `decompress-backup` | Closed independent backup only, pinned hashes, bounded expansion, integrity/identity verification and a new destination. Original retained; no compression of a live DB. SQLite inspection uses private copies so it cannot create sidecars beside the sealed source. |
| `preview-vacuum` / `vacuum` | Current Lead and active maintenance session; explicit stopped-writer/service evidence, zero retained holders, matching verified backup, window approval and fresh space checks. Space is observed, not reserved. Preview hashes exclude changing time/space observations. |
| `resolve-maintenance-operation` | Unknown VACUUM remains pending and blocks retry/exit. Only an explicit matching stopped-process observation plus actual integrity checks can abandon it; this does not certify completion, and the old operation ID remains retired. No automatic takeover or retry. |
| `restore` / `restore-migration-backup-2-to-3` | New target only. Ordinary restore-new-target preserves source schema; current restore is schema 4. Historical schema 2 uses the explicit 2-to-3 conversion route, and schema 3 requires an explicit 3-to-4 migration. Neither migration runs automatically. Verify backup authority/hash and retained allocations, rotate generation, revoke obsolete execution authority and require reconciliation. Never inherit an old maintenance session as current permission. |

Archive/prune/schema transitions use atomic business receipts. Checkpoint and backup compression/expansion return `receiptCommitted: false`; repeated IDs are not exactly-once guarantees for physical filesystem effects. Existing destinations conflict. After a lost response, inspect retained artifacts and hashes before deciding on another attempt. VACUUM commits a durable start before the physical call and records its observed final result afterward; interruption between them remains unknown. A nonzero CLI exit can accompany a retained failed maintenance receipt, so preserve that result rather than retrying it blindly.

Protect generated local scopes before disk writes. In Git projects initialization can append a bounded literal `/_work/<slug>/` rule after checking tracked files and include conflicts; existing effective in-project literal policy may be reused. Existing-board maintenance/restore and their output scopes are audit-only and must already be protected. An authenticated ordinary backup can protect its new bounded Work destination. Custom paths need an effective literal policy; global/private excludes and wildcard-only coverage are insufficient. Stop for tracked/include conflicts without untracking. Non-Git projects are not initialized as Git. These checks complement [artifact protection](generated-artifacts.md), not permission to modify arbitrary ignore policy. Private inspection scratch is cleaned on normal success/rejection; forced termination can leave a private directory, never authority to scan/delete unknown temporary files.

The installable Skill runtime is a generated package artifact, not hand-maintained source. Deployment consumes the selected GitRef's already-built runtime only after validating the source/runtime manifest and artifact correspondence. Installation must work offline and must not execute a build from the selected GitRef or download/install dependencies. Unknown or mismatched artifacts fail closed; deployment does not delete or migrate project queue data. Runtime availability, command names, query bounds, and supported platforms are limited to facts verified by the current implementation and packet, not examples or planned work.

When running the package test suite against `CurrentPayload`, provide `-TaskBoardManifestSha256` and `-TaskBoardAppSha256` using hashes approved after review of that candidate payload. Do not derive expected hashes automatically from unreviewed source; see [setup and diagnostics](../../../docs/setup.md) for the opt-in runner command.
