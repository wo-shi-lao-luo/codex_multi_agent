# Role routing

At the start of authorized execution, including work performed by the Lead alone, apply the [default Board activation checkpoint](task-coordination.md#default-activation-checkpoint). When using the queue, apply the [task coordination contract](task-coordination.md) for Lead-owned assignment, host-capacity/dispatch reconciliation, actual role and model evidence, and readonly-role proxy reporting. The queue does not create or resume host agents.

The Lead classifies a request before delegating.

Same-task peer exchanges are allowed only under the Lead's explicit handle-scoped grant and the [bounded peer communication contract](peer-communication.md). Role routing still owns task creation, role selection, issue ownership and escalation.

For bounded external research, the Lead may select `team-researcher` under the [external research contract](external-research.md). The Lead supplies the sanitized question, source/version needs, one shared task budget, authorized peer set and handoff target. Authorized peers may communicate directly with that existing researcher for scoped clarifications or follow-up, using host-supported messaging; the Lead retains scope, lifecycle, integration and decisions. Missing search or communication capability is reported for Lead routing. This does not create a standing researcher, add budget to diagnosis/repair, or authorize external side effects.

When the Team entry is explicitly invoked or task-matched to engineering work, use the [shared workflow-routing contract](workflow-routing.md) to choose the applicable existing mode from intent, authorization, evidence, and risk. The user need not invoke a second Skill. This does not change role requirements or permission boundaries; no router child is created. A simple factual consultation may need no role call.

Do not delegate a role merely because it exists. Delegate bounded, independent work with a requested output. Classify scope and risk rather than using file count or line count as a proxy: a one-line permission, data, deployment, security, or compatibility change may be material or high risk. A `$team-debug` investigation may perform bounded diagnostic reproduction and controlled experiments under its current contract, but that does not authorize a production repair; an authorized code repair enters the `$team-dev` implementation requirements and does not bypass its roles or verification.

Targeted test discovery is an optional evidence lookup, not an additional coverage owner: only request it after the Lead or Tester supplies the relevant behavior/module boundary, and only when the test map is not already cheap and reliable to locate. Explorer reports paths, IDs, scenarios/assertions, commands, runner/boundary and dependency/artifact facts plus gaps; it does not judge adequacy, passing status, skips or acceptance. Avoid duplicate broad searches by the Lead and Tester. Named-role preflight and gating still apply when Explorer is materially needed. The Lead applies the user's existing authorization; only the user may expand it for additional external/paid operations or budgets.

For standard-path code-changing `$team-dev` work, follow the responsibilities and independent-gate obligations in the [execution contract](execution-contract.md). Select the mode before applying these domain routes: they specify responsibilities when the selected mode delegates them and do not instantiate roles based only on file type, module count or AI/UI/data keywords. In particular, a bounded task spanning known loader and client files need not be split among owners solely for that reason. For standard-path mixed tasks, assign a second Tester only for distinct required assertions or risks, keep one canonical packet owner, and preserve software integration coverage. Do not force Explorer, Architect, multiple implementers, or document categories when they do not fit. When a separate Tester is needed for harness distribution/helper/package behavior, use ordinary `team-tester`. Route scripts/configuration to an existing domain role that matches the actual scope. A behavior-changing Skill, policy, or agent-routing/configuration change to the harness is implementation work, not trivial prose; instruction-only harness content uses `team-docs-maintainer`. The Lead may fulfill serial responsibilities without a user-approved exception, but must not represent self-check as independent evidence or replace an independent gate with the Lead. Role unavailability or host capacity changes neither the risk classification nor the evidence required.

The Lead may own serial implementation and perform test-planning/check responsibilities without a separate user-approved exception. Standard-path packets, TDD, checks and evidence remain required. Lead-run checks are self-check, never independent Tester evidence. Use separate identities for required independent gates or demonstrated parallel/context/cost benefit. If an independent gate cannot be staffed, pause that gate and report the limitation.

The Lead's brief start declaration records task type and risk, applicable standards, intended named roles/ownership, and planned checks. At close, reconcile that declaration against actual selected roles, completed checks, evidence and remaining gaps. Keep both records proportionate to the task and reuse existing Work/Verification records or stage packets.

## Named-role preflight and invocation

These rules apply when a listed Team workflow is active or `$team-code-maintain` is invoked; they do not otherwise activate a workflow in every ordinary Codex conversation. Pure consultation and read-only planning/review/investigation do not inherit the `$team-dev` implementation-agent minimum. Team workflow use does not require an agent for every file; standard-path evidence obligations apply to noneligible code-changing `$team-dev` work and behavior-changing harness edits; role instances depend on independent gates or justified parallel work. Use the [risk-proportional light path](execution-contract.md#risk-proportional-light-path) for its narrow eligibility and role rules. `$team-code-maintain` is a bounded formatting-only route and does not force the full `$team-dev` lifecycle for genuinely nonbehavioral maintenance. Serial Lead responsibilities do not replace any required independent role or gate.

Before delegating, list the roles needed for this task and check their exact names against the **active session's tool role catalog**. Record that availability evidence in the Work contract. TOML files on disk, an installed receipt or the planned role map do not prove that the current session exposes those roles. Check only needed roles; do not block a small task on unused roles.

Select the exact named role through the host's supported role selector. For a spawn tool exposing `agent_type`, explicitly pass e.g. `agent_type: "team-tester"`; use an equivalent documented selector on other hosts. A `task_name` such as `tester`, role text in a prompt or copied model settings does **not** select a named role. Do not omit the selector or silently replace a required Team role with `default`, `worker` or `explorer`. Follow-up messages cannot turn a previously created generic agent into a named Team agent; retain its original identity when reusing it.

Immediately after each spawn, check the selector actually sent against the planned role and inspect available returned identity before allowing dependent work to proceed. If a needed role is unavailable, a spawn fails for a reason other than confirmed host-capacity exhaustion, the actual selector differs without prior approval (e.g. planned `team-tester` but sent `worker`), or returned evidence confirms the wrong role, pause the affected delegation and dependent work. Stop or interrupt affected active work when appropriate, preserve existing edits, and ask the user with the evidence and options: make the intended role available in a fresh session, approve a specific alternative, or defer the dependent work. Installation, configuration/model changes and reverting edits require their own authority. Independent authorized work may continue. Record the user's decision before any alternative invocation; task urgency is not fallback permission. Keep any wrongly created agent in the actual roster even when the host returned only an ID.

If the host explicitly rejects a correctly selected spawn because its thread capacity is exhausted (for example, `agent thread limit reached`), keep that same named-role task queued and let dependent work wait. Retry that role only after the host reports capacity or meaningful host/session progress changes, such as a later workflow turn; without a capacity report, make at most one bounded retry after such a change, not repeated blind retries. A successful retry confirms only that the host accepted that spawn at that time; it does not prove which slot became available or a durable capacity. Do not silently substitute another role. If the retry is still rejected, keep the task queued and continue only with independent work that fits confirmed capacity. This exception applies only to host-capacity rejection, not missing roles, other spawn failures or identity mismatches.

## Adaptive child-thread concurrency

Use a recommended ceiling of up to six concurrently open spawned-agent threads across the Lead's whole session; the Lead is excluded. This is a ceiling, not proof that six threads are available or a target to fill. A configured value or tool-catalog slot count does not establish live capacity. Follow the capacity the active host actually enforces, and do not assume a completed result or handle releases an open-thread slot unless a supported host status or operation confirms it. If capacity is unknown, stay within confirmed availability.

Treat 2–3 concurrently open child threads as a normal-work heuristic, not a minimum or a required simultaneous role count. Medium work may use 3–4 and large work 4–6 only when the additional work is genuinely independent, its inputs are ready, and actual host capacity permits it. Before expanding beyond three, briefly explain the reason to the user and record in the existing Work contract or Review coverage record each distinct output, ready inputs and dependencies, nonoverlapping write boundaries, and the integration owner and plan. Do not create a new planning record for this purpose.

Parallelize only work that can proceed independently: for example, read-only checks, disjoint file ownership or isolated fixtures. Keep shared mutable test state and dependent outputs sequential. Keep one production writer by default where implementation is involved, and preserve Tester planning/verification and independent Reviewer sequencing and obligations. Child agents do not create agents, manage a roster, or create/reassign tasks. Only when the Lead's initial grant explicitly permits it may a child use a host-supported follow-up to resume a named existing recipient for that recipient's original task, ownership and budget; this resumes granted work and does not orchestrate new work.

## Child-thread lifecycle

These rules cover only child threads created or explicitly reused by the current Lead for this Team workflow, not unrelated user chats or threads. Reconcile the task-owned roster and required named roles at task start and before spawning, at child handoffs and phase changes, after a capacity rejection, and at task close. Reuse eligible work only under its original handle and selected role; a task label or follow-up cannot convert a generic child into a named role.

## Lead progress inquiries

For substantial delegated work, use the progress checkpoints in the [execution contract](execution-contract.md#migration-batches-and-progress). Proactively send the exact child a supported, noninterrupting status query when evidence shows a missed task checkpoint, a substantial forecast deviation without a current explanation, stale substantive status with no known progress, or another branch finishing while unresolved workload is concentrated there. A running UI, elapsed time, or diagnosis count alone does not establish a stall.

Ask for the current phase (editing, typechecking, test execution, waiting, or other), actual last result/delta, remaining error groups and dependencies, process health when applicable, next output/checkpoint, and needed help. Use existing messaging/status tools only; no timers, daemon, universal cutoff, frequent polling, or new records. No response leaves status unknown and is not permission to kill or reassign. If healthy, continue with a concrete checkpoint; route evidenced root causes to the fitting owner; consider a safe split/transfer; return scope or decisions to the Contract/Lead. If health cannot be established or evidence shows material divergence or an unapproved operation, follow the [repair and diagnosis loop guard](repair-loop-guard.md) pause/human-decision gate. Do not force interruption or grant extra scope, budget or retry allowance.

Before transferring same-path ownership, follow [file ownership](file-ownership.md) for the exact-path freeze, process-stop and evidence/state handoff. Early review validity and affected-scope retest/rereview are defined in the [execution contract](execution-contract.md#migration-batches-and-progress).

At each checkpoint, first assess whether existing work can be reused. If a delegated child is complete, handed off, no longer needed, and not reserved for a required Tester/Reviewer gate or other work, close it promptly through a documented operation available in the active host. Before closure, preserve its results/evidence/open issues and ensure all writes/process ownership is ended or safely transferred independently of the child thread. If ownership or transfer is uncertain, keep it open and report the blocker. Never force-stop an active, waiting, needed, reserved, or uncertain child just to create capacity. Completion, interruption, UI archival, or disappearance from a view is not itself closure or capacity evidence.

After a capacity rejection, inspect eligible same-role reuse and safely closable task-owned children before deciding next steps. Keep the exact named-role work queued; do not treat Lead takeover as an automatic capacity workaround or bypass its user-approval and independent-role gates. Close only using the documented host operation and exact child handle. If no close operation is available, report that limitation and queue the role or reuse an eligible child; do not invent a tool or substitute archive/delete/interrupt. Capture the result. A successful supported close is lifecycle progress and may justify one bounded retry of the same queued named role, even without a numeric free-slot field; it does not prove numeric or durable capacity. Failed/unknown closure justifies neither retry nor release claim. Otherwise use only the existing capacity/progress retry gate above; do not blindly repeat an uncertain close.

Record lifecycle events in the existing Work/Verification record or stage packet, not a new registry: original handle and selected role; handoff/open issues; write/process ownership ended or safe independent transfer; reuse/close decision and documented operation/result; exact-role queue/retry and evidence. Retain every created child, including closed children, in the final actual-agent roster with final known status. Never claim a slot was released unless the host separately confirms capacity; unknown remains unknown.

## Invocation evidence and reconciliation

Keep a concise invocation ledger in the existing Verification record or applicable stage packet; do not introduce a separate raw-log store. For each actual creation, record:

- planned role and scoped task/owner;
- active catalog availability evidence and the exact role-selector argument sent;
- returned agent ID/task handle and any host-reported role identity;
- source profile expectation, active tool profile and resolved model/effort **separately**, when relevant and available;
- status, retries/reuse, deviations, user decisions and an evidence reference.

The call argument proves which role was selected; a returned ID proves creation, not independently the loaded role/model. If the host supplies no role or resolved model, mark it `unknown`/`not reported`; never infer it from task labels, prompts, source TOMLs or the parent model. A source profile differing from the active tool definition is an environment discrepancy, not proof of the inference model. Disclose it; if matching that profile is a prerequisite for the task, pause dependent profile acceptance and seek direction instead of silently claiming it was loaded.

At Verify, reconcile planned roles, actual selector arguments and returned identities. A confirmed unexpected identity remains a deviation even if the result was useful. Capture each created retry/replacement as its own entry, including failed/interrupted agents; a failed spawn with no returned ID is an **attempt**, not a created agent. Reused agents keep their original ID/selection and list the additional assignment.

## Final actual-agent roster

At every Team workflow close, the Lead must show the **actually created/used** child agents in the final user-facing response using the [handoff format](handoff-format.md). Include their ID/task handle, selected role, task and final known status, plus role/model limitations or approved deviations. Include all created agents for this task, not only successful ones; distinguish failed creation attempts. If none were used, say so explicitly. Link the existing evidence record when available without exposing sensitive raw logs or exact home paths. Do not replace the roster with planned roles or merely say "the team reviewed it."

These are inspectable workflow obligations. Package validation guards discovery links/resources, not future spawn arguments or an unbypassable runtime gate. Lead and independent reviewers inspect actual call evidence; an authored ledger alone does not authenticate execution. See the official [Codex subagent configuration guide](https://learn.chatgpt.com/docs/agent-configuration/subagents) for the distinction between built-in and configured custom roles.

Apply the [UI delivery contract](ui-quality.md) to preserve the original product goal, visual baseline and final-page verification when routing UI work. Small demos normally retain one implementer; page ownership does not remove modular code or file boundaries.
